# Independent template reviews and external transfer

Subsequent implementation: the
[repair and method-delivery record](2026-10-28-review-method-transfer.md)
preserves the corrections, normal-template probes, fresh rechecks and consumer
trial. The first findings and factual correction below remain historical
evidence; they are not the current implementation status.

## Request and supported judgment

The owner requested two independent agents with identical review assignments
to revisit the earlier template problems, and a third fresh external consumer
to decide what it would take away, try using it, and explain any transmission
failure. This is review work, not authorization to implement a new repair.

The supported judgment is **partial improvement**. The template now conveys a
useful judgment method, a concrete task procedure and outcome-based stopping.
A fresh consumer applied that method to an isolated task. Complete source
delivery and normal template adoption still have reproducible gaps; some
analysis requirements have an overly broad applicability boundary. The previous
claim that the template change was complete is reopened at those boundaries.

## Context and independence

All three agents used `fork_turns=none` without model overrides. Reviewers A and
B received exactly the same original owner requirements: usable SOPs, global
versus mandatory domain detail, authority/strength/boundaries, preservation of
purpose, supported positive judgment and sufficient stopping. They also received
the owner's correction that visualization was a symptom, not the template goal.
They selected their own inspection paths across the actual project.

Consumer C received the external-transfer question without that issue checklist
or the executor's intended mission answer. It started at normal entrypoints,
recorded an initial understanding, selected material, and tried it in an
isolated fictional project. No agent received another first judgment or the
executor's defense before returning its first report.

The model/settings were inherited from the root; no model variation is claimed.
They share repository sources and model assumptions. Their separate probes
corroborate particular observations, rather than constituting a vote that settles
the whole outcome. The consumer question and supplied context both differed;
the comparison does not isolate either factor's effect.

Baseline was `fa01192f094585ff0c1aaa6942ac04e63a11983a` plus the frozen
uncommitted tree. Root checked all 120 recorded source digests after the first
reports: none changed. Agents had read-only repository access, private local
temporary probes, and no external export, account or browser operations.
Evidence and lifecycle corrections below were written after review closed.

## Confirmed reading and integration gaps

### Risk definitions are outside the global delivery set

[Formal profiles](../contracts/agent-execution-discipline.md#vocabulary-and-risk-profiles)
define routine, material and high-risk work, including that a compatible public
API addition is material. Task context selects risk, route and completion units,
but the definitions lie outside their boundaries. Actual core preparation emits
none of the three formal definitions. Root reproduced the omission.

This is a source-delivery gap affecting the decision about execution depth.
No actual agent misclassification was observed. Fixing it requires a complete
dependency, not merely another instruction to classify carefully.

### Product-template metadata conflicts with reader validation

The [backend template](../../templates/backend-change.md), generic contract and
cross-stack template omit `contract_role`. The established checker defaults a
missing role to product at `scripts/check_docs.py:603`; the reader instead
rejects it at `scripts/rule_reading.py:294`.

Both reviewers reproduced `owner requires a valid contract role` after placing
a normal service contract at its canonical destination. Adding only
`contract_role: product` gets past that check. Root independently reproduced the
metadata failure using the actual template. Its probe retained other template
placeholders, so it is not presented as a complete product-adoption check.

The hidden precondition breaks the normal template-to-reader route. Existing
explicitly classified governance contracts work, which explains why checking
only the source template's own owners did not expose this case.

### Service and cross-stack detail are not wired into preparation

AGENTS requires complete backend and cross-stack reading for matching tasks.
Their units exist, but their templates declare no corresponding reading
dependency. After correcting the metadata in a temporary service owner,
concern preparation emits core plus the owner and omits backend detail. B also
tested compatibility/state/reliability together without obtaining the domain
units. Root reproduced the backend omission.

An agent that follows the manual AGENTS navigation can obtain those rules.
`READING COMPLETE` correctly describes the selected declared closure, not every
semantic obligation. Nevertheless the recommended executable route still leaves
the precise missed-detail failure the owner wanted to remove. Unit existence
and a successful direct heading read do not establish a connected task route.

## Domain applicability counterexample

[Analysis scope](../contracts/data-analysis-discipline.md#scope) includes general
dataset exploration, metrics and rankings. Its invariants require re-runnable
functions and adjustable parameters; analytical marks must click through, and
acceptance lists a click-through pass. A fixed CSV-to-PNG report with a stated
source, denominator and concise conclusion triggers analysis but cannot provide
clickable PNG marks.

Both reviewers identified this specification counterexample. The question
checklist permits skipping unreached stages, but that does not explicitly bound
the separate mandatory invariants and acceptance requirements. This risks
promoting a particular analytical-product form into every analytical task.

This is a supported scope risk, not an observed real adopter being forced into
an application. It does not establish the cause of the earlier visualization
detour. A repair should preserve traceability and reproducibility while making
the applicable delivery forms and conditions explicit.

## External consumer result

Before seeing the issue list or old verdicts, C understood the project as an
engineering judgment and delivery discipline, with no product implementation.
It chose to take the procedure for requested outcome, facts, decision authority,
boundaries, ownership and completion evidence. The README's value ranking and
separation of checks from task success helped transmit that priority.

C selected complete source units and task guidance from five files, totaling
1,519 lines and 97,117 bytes. It also carried the risk-profile definitions and
wrote its own short portable note. The note is a consumer synthesis, not an
already supplied repository artifact. No checker, CI, policy manifest, personal
history or full template directory was carried into the task.

The fictional target was a small existing JSON directory-listing CLI. C kept
the target README as interface owner, updated that owner before code, chose a
routine bounded route, and verified actual process output and effects. Nine
cases covered normal/empty/Unicode output, missing or non-directory input,
argument errors, actual permission denial, and corrected-input retry. Successful
JSON remained byte-compatible; failures used the specified channels and exit
status; retry recovered; project contents and mode snapshots were preserved.
The unreported extra-argument case was found and guarded as a sibling mechanism.

This is evidence of applied method rather than vocabulary recall. The root
inspected the actual result record, initial understanding, selection manifest
and task decisions. C had ordinary programming capability and host rules, and
there was no ungoverned control group; the code result cannot be attributed
entirely to the template. No second fresh recipient or long-term reuse was tested.

## What transfers, and where transmission costs remain

The core judgment method and its priority transfer. The task procedure and
worked decisions supply usable actions, including retaining an existing owner
and stopping at an explicitly bounded result. The hypothesis that the public
method can only be decoded through private conversation is not supported by C.

The portable minimum still required C to select and combine nearly 97 KB of
source. The default core itself is 88,704 bytes. These are observed reading
sizes, not proof of unreasonable cost or of measured efficiency. A cold-start
or later-recipient benefit remains unmeasured.

The project also distinguishes selective extraction from a full formal learning
survey, but a new consumer must discover that distinction. The full
[learning path](../contracts/project-adoption.md#learning-and-personal-context-have-a-bounded-entry-path)
expects comparison with an owner's repeated corrections and the behavior of
already-loaded rules. A first-time visitor may have no such history. That is
a route/precondition adaptation cost; missing history must remain unknown.
C completed bounded extraction, not the entire formal learning route.

## Verification and disposition

A and B each ran all 164 unit tests and the documentation checker successfully.
Both observed the pre-existing independent-adoption-review advisory. These
passes coexist with the reproduced normal-use defects; their current coverage
does not settle the requested template outcome.

Root confirmed the three reading/metadata gaps and inspected the external trial.
The review round is complete. The earlier implementation plan is reopened for
the established acceptance gaps; its prior source-delivery and example results
remain narrower evidence. No behavioral rule, reader code, template or product
was repaired during this review. The source and dependency gaps should be
resolved before another complete-template judgment; the analytical boundary
and small-extraction route need proportionate clarification and trials.
