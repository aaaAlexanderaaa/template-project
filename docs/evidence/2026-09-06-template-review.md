# template-project：围绕用户承诺、实际效果和必要上下文改进

本记录是受请求进行的研究和设计建议，不改变当前项目契约。`historical` 表示这是一个有日期的研究快照，不应加入每次开发的必读材料。

研究基线为 `b0e5a8196fc529cb38da76d29d1d00c06e128403`。本次读取了本地仓库、两份参考回答和相关第一方资料，复跑了仓库的 111 项测试及文档检查，均通过。没有运行各家商业 agent 的兼容试验，也没有获得两个下游事故的原始任务轨迹。因此：仓库结构发现的置信度高；事故成因解释与改进效果的置信度中等或待验证。

**我的核心建议：把模板的工作单位从“完成一个合规的变更流程”，转向“兑现一个有边界的用户承诺，并说明实际发生了什么”。** 保留已有的授权、证据和所有权纪律；减少需要 agent 自行记住的流程；让模板自身接受真实任务检验。品牌适配服务于这个目的。

这并不要求另建通用 agent runtime、memory 数据库、任务调度器或需求管理平台。很多必要改进可以在现有契约、构建入口、验证报告和交接记录里完成。

## 对两份参考回答的取舍

## 共同基础不能只取 feature 的交集

“大家都支持某个文件、hook 或 MCP”不足以构成模板基础。文件可能没被加载，hook 可能不阻断，子任务可能继承全部历史，也可能只收到一句任务描述。共同基础应是可以跨运行时保持的语义：

1. 用户要得到什么、什么已经授权、什么不在本次范围内。
2. 当前事实在哪里，适用规则由谁拥有，冲突如何处理。
3. 执行会读取或改变哪些对象，产生哪些外部效果。
4. 中断或换执行者后，怎样区分已完成、未完成和结果未知。
5. 什么观察能够支持完成声明，什么仍然没有得到证明。

这些能力即使通过普通文件和 shell 手动实现，也应保持。没有 hook，只能表示自动化较少；若缺少必要的权限控制或观察能力，则只能限制相关工作，不能偷偷降低承诺。

MCP 标准规定连接与能力协商，Skills 规定程序性知识的载体与渐进加载。它们都不替项目决定目标、授权或交付是否完成。[MCP maintainers, 2025-11-25, Architecture](https://modelcontextprotocol.io/specification/2025-11-25/architecture)；[Agent Skills maintainers, 检索于 2026-09-06, Specification](https://agentskills.io/specification)。这是两个不同标准的作用域比较，并非所有产品采用同一实现的证明。

## 仓库的主要问题：价值表达与执行诱因不对称

**事实，高置信度：** 当前规则没有把“过测试”定义为最终目标。它明确写了用户结果、失败恢复、质量属性和生产观察；也已经有按风险执行、并行书面协调、授权内自主选择和文档退役。把项目批评成完全没有这些纪律是不准确的。[开发纪律](../contracts/development-discipline.md#outcomes-before-means)、[执行纪律](../contracts/agent-execution-discipline.md)、[治理边界](../contracts/governance-decision-boundary.md#delegated-engineering-work-proceeds-by-default)。

**风险，中等置信度：** 抽象价值和具体动作的反馈强度不同。“关心用户结果”宽泛，而“先填契约、写 failing test、跑检查、更新状态”能立即完成并获得通过信号。agent 可能逐渐用后一组动作代替前一组判断。即使完全理解规则，也可能因为缺乏领域知识、漏掉副作用或共同误解需求而交付错误。这些原因需要分开验证。

`agent-execution-discipline.md` 的 `enforced` 在正文里限定为模板和结构面，正文也承认真实并行采用效果仍未验证。这不是必然的逻辑矛盾；但一个整篇文档的状态容易让接收者扩大理解。建议让重要完成声明直接关联其对象和证据，例如“模板结构通过”“装载试验通过”“实际用户场景通过”，不要把它们汇成一个没有范围的绿色状态。

`engineering-judgment-discipline.md` 明确承认“遵循全部流程仍可能做错东西”，但尚为 target/pending。其配套计划已经完成，因为那次任务的终态就是起草 target，不是落地应用。不能以计划 completed 为由指控虚假交付；可以指出真正需要的工程判断尚未有实际采用证据。[工程判断契约](../contracts/engineering-judgment-discipline.md)、[对应计划](../plans/2026-08-28-engineering-judgment-discipline.md)。

因此，优先级不应是继续增加规范覆盖面，而是建立一个能让“规则全遵守但用户仍没得到结果”的变更明确失败的验证入口。

对七阶段的具体改法，是把必须达到的要求与实现方法分开：目标与授权明确、重要事实有依据、结果得到适当观察、失败和恢复得到验证，这些仍是交付要求；fixture-first、先写 failing test、先做运行探针或先验证构建入口，则按问题选择。现有规则已经允许说明不适用，建议进一步让方法选择成为正常路径，而非先套固定阶段再逐项申请例外。选择成本低的证据也有前提：它必须足以支持所作出的完成声明。

## 把功能性与非功能性承诺落实到具体情景

建议扩展现有契约的 outcome/acceptance matrix。对于可能影响交付的行为，说明：谁在什么条件下触发；读取或改变哪个对象；需要产生什么效果；禁止产生什么效果；必要时说明次数、时限、顺序、质量边界和失败后的下一步。每条承诺由原契约拥有，项目层只汇总引用和验证状态，不再复制一份独立需求库。

“承诺”在这里指产品或工程交付承诺。现有 `promise[...]` 的语义是到期的未来协调事项，**不要复用那个字段当产品功能清单**。

功能与非功能要同时表达，但不用为不存在的风险填满所有类别。例如“能检查文件变化”是功能；“同一轮多个点击只启动一轮工作”“不越过已声明的网络预算”“不把未知显示成未变化”“结果解释清楚下一步”分别约束资源、可靠性、真实性和可用性。这些是同一用户情景的不同验收面，不是互不相干的附录。

这与 SEI 用具体情景说明质量属性、Google 用用户目标组织体验指标的方向一致；本报告提出的具体表结构仍是设计建议，并非这两项来源验证过的通用方案。[CMU SEI, 未标日期, Quality attributes](https://www.sei.cmu.edu/library/reasoning-about-software-quality-attributes/)；[Rodden、Hutchinson、Fu, 2010, CHI publication](https://research.google/pubs/measuring-the-user-experience-on-a-large-scale-user-centered-metrics-for-web-applications/)。

用户提出的四类偏差，可以转成双向验证：从声明找对应效果，也从观察到的效果反查授权和声明。

| 偏差 | 需要观察什么 | 能击中缺陷的试验 |
|---|---|---|
| 声明存在，实现缺失 | 用户入口是否真正触发所需结果 | 保留内部函数和单元测试，断开按钮/事件注册，交付验收应失败 |
| 未声明的效果 | 请求、写入、权限变化、通知、后台任务是否越过范围 | 加入偷偷预取或自动写配置，观察应发现额外效果 |
| 次数过多 | 按实体和操作身份统计实际尝试及成功效果 | 连点、双标签页、重试、恢复后重放，检查是否重复执行 |
| 次数过少 | 必须完成的结果在允许时限内是否出现 | 换实体、切账号、缓存过期、失败重试，检查去重是否错误压制新工作 |

四类不是完备分类。还必须区分：对象或内容错误、顺序错误、迟到、部分更新、只在一端可见、越权、结果正确但成本过高，以及用户无法理解结果。总次数刚好为三，并不证明检查了正确的三个对象。

次数也不能只数工具调用。一次调用可能发出多次请求；一次超时可能已经在服务端产生效果。应区分用户意图、逻辑操作、网络尝试、实际状态变化和通知。AWS 的幂等性经验与 Google 的重试预算分别支持身份和负载这两类边界。[Malcolm Featonby / AWS, 未标日期, Idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)；[Google SRE, 2016, Handling Overload](https://sre.google/sre-book/handling-overload/)。

这里只建议在重要边界观察必要事件，不要求对全部内部函数建立事件平台。有限测试只能覆盖声明的输入、时间窗口和观察面；“没观测到”必须能与“确定没发生”区分。某些只会在生产暴露的承诺，应保留有限试运行、观察和回退条件，不能通过打勾消除未知。

## 用浏览器插件的 check 功能验证这套方法

以下是设计示例。未读取该插件源码和目标网站协议，因此不是可直接部署的实现规格。

**首先明确用户要检查什么。** “三个 JS 变化了”至少可能指 URL 换了、内容字节换了、三个职责换了实现，或依赖行为不兼容。这些目标要求不同的证据。相同 URL 可以换内容；不同文件名可以提供相同职责；打包后的文件数量也可能变化。它们不能都叫“检查成功”。

应从已有事实出发确认脚本身份来源：构建 manifest、页面实际加载记录、明确的模块导出，还是只能做启发式匹配。若逻辑职责被拆到五个文件，关系应允许一对多；多个职责合并时也允许多对一。不能按位置或相似文件名强行配成三对三。

| 要作出的工程决定 | 候选做法及适用条件 | 必须能验证的结果 |
|---|---|---|
| 是否新增网络请求 | 已有页面或构建证据足够时先复用；不足时才考虑对有限候选做主动检查 | 每一类新增请求都有用途；额外权限的代价也计入比较 |
| 用什么判断变化 | 字节一致、资源版本、职责兼容分别选证据，不以 URL 或 ETag 无条件替代全部含义 | 检查类型、基线、观察时间和证据强度可说明 |
| 如何去重 | 明确页面版本、账号/环境、逻辑对象和当前轮次；合并同轮并发工作 | 同轮重复触发不放大工作；新实体、新版本或过期数据不会被旧 key 压制 |
| 如何停止 | 为尝试数、总请求量、时限和并发设相称边界；限制适用的失败重试 | 达到界限便返回明确状态；不能无限轮询、无限扩展候选 |
| 如何应对映射不唯一 | 展示候选、依据和不确定性；是否改配置由已接受的产品规则决定 | 不自动截成三个；不把部分匹配当完整成功；不吞掉新增或消失对象 |
| 更新之后怎么办 | “检测到变化”“确定新映射”“替换配置”“验证兼容”是不同动作 | 用户知道发生了哪一步、哪些文件受影响，以及接下来能做什么 |
| 中断后怎么办 | 区分进行中、失败、部分结果和结果未知；重启后核对已发生工作 | 不仅刷新后能继续，还要证明不会重复消耗、误报新鲜度或丢失必要重试 |

“被动观察优先”也不能变成新教条：Chrome 的 `webRequest` 看不到某些内存缓存命中，也不能直接把请求元数据等同于完整脚本内容。证据不足应显示未知，不能为了零新增请求而假装判断完成。[Chrome for Developers, 当前 API 文档, Caching](https://developer.chrome.com/docs/extensions/reference/api/webRequest)。

HTTP 条件请求可以减少传输，但 `304` 仍然有请求成本，弱 ETag 不保证字节一致。机械地先 `HEAD` 再 `GET` 还可能增加往返。具体选择取决于所需的“变化”语义和目标服务的响应能力。[Fielding、Nottingham、Reschke, 2022-06, RFC 9110 §13.1.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.2)。

“最少、最小必要”也需要限定：是在满足多长的新鲜度、哪种检测保证、什么权限和成本条件下最少。更少请求可能意味着更新发现更慢；完全禁止主动请求可能让某些变化无法确定。工程师应先找能够满足既定目标的低成本方案，只有真正改变目标或风险承诺的选择才交给用户。没有目标网站的规则和实测，无法保证绝不会封号，更不应编造一个通用安全频率。

这个案例的最小有意义验收不是“mock 返回变化时按钮变红”，而是运行打包后的扩展，控制页面版本、账号、缓存和时间，观察真实请求、持久化状态和界面结果。覆盖并发点击、双标签页、超时、重启、三变五、五变三、无变化、映射不唯一，以及权限/来源不足。预先准备的受控环境承担大部分验证，不对真实账号做压力试验。

## 上下文减负需要改变读取依赖

实测入口三文件共 **30,973 字节**：`AGENTS.md` 14,512、`ARCHITECTURE.md` 6,012、文档地图 10,449。再加开发、执行、治理三个契约，示例阅读路径为 **107,449 字节**；它们的来源与协调历史章节合计 16,002 字节。这些是磁盘字节，不是自动注入 token，也不代表每个任务都必须读完整六文件。

130KB 不自动证明模块化差：任务本身可能复杂。更有辨别力的问题是，修改一个局部行为是否必须恢复无关领域知识；一个规则变化是否要求更新很多内容副本；接手者能否快速找到当前承诺和未完成工作。把大文件平均切成十份，不会解决这些依赖。

建议分开三个使用面，可以先在一个仓库内完成，不必新建多个产品：

- **维护模板的人需要的资料：** 原理、取舍、研究、案例和历史，用于维护与学习，按需读取。
- **采用项目需要的当前事实：** 它自己的边界、功能/质量承诺、运行入口、当前决定和必要理由。可以复用原理，但不用每次学习模板的发展史。
- **正在执行任务的人需要的输入：** 目标、授权、有关契约、代码位置、运行方式、当前进展与关键未知。父任务、单 agent 或子 agent 都消费这一层。

入口保留无法从代码恢复的核心约束，以及“这类任务去哪里、怎样运行、怎样验证”的简短路径。领域细节按触发条件路由。确有重复读取成本时，可用简单脚本生成当前任务的引用清单；生成内容必须能回到唯一 owner，不能变成第二套规范。

归档前，先把仍生效的决定和必要理由合并到当前 owner，再把执行流水和被拒绝方案留作历史。已完成计划不继续充当状态板。删除的判据是是否仍支持决策、审计或恢复，而非文件够老。长项目交接只更新仍在进行的工作，不重写全部历史。

需要验证减负有没有丢掉约束：给新会话同一局部任务，比较找到正确入口前的读取量、遗漏的约束、过期知识使用和最后结果。缩短 AGENTS 或改成按需检索本身并不保证改善；相关实证的结论并不一致，见后文。

## Memory 与 subagent：保留必要规则，按实际能力启用机制

memory、压缩摘要和交接都涉及一个问题：派生信息是否仍适用于当前任务。项目应明确它们可以提供线索、偏好和经验，但不能自行变成产品授权或覆盖已确认的规则。事实也不能被“文档更权威”压掉：观察与契约不一致，意味着需要修实现或修契约的冲突，而不是删除不合意的观察。

对于会影响决策的经验，保留来源、适用范围和失效条件；能够从代码重建的事实不必重复沉淀。普通临时线索可以留在原生 memory。不要创建 memory 数据库来解决一条规则优先级问题。OpenAI 本身也要求把团队必需指令留在版本化文档中，Anthropic 则明确区分自动 memory 和人工项目指令。[OpenAI, 当前 Memories](https://learn.chatgpt.com/docs/customization/memories)；[Anthropic, 当前 Memory](https://code.claude.com/docs/en/memory)。这是两个独立厂商对职责分离的描述，不证明任何配置都不会发生覆盖。

分工先看依赖和集成成本：独立调查和只读审查适合分出去；共享状态语义还没确定时，多人同时写不同文件也可能冲突。默认选择能完成工作的简单拓扑，不能强制单 agent，也不能用数量充当质量信号。

每个较长或会写入的子任务，复用现有计划/交接记录交代六件事：目标及父目标；允许的写入与副作用范围；基线和实际工作环境；必要规则与证据入口；预期产物与验证方式；无法完成时怎么返回。短只读任务可由原生调用记录承载，不需要另建表或人工接收确认。

回收时读取产物和验证结果，处理过期基线、冲突、失败和取消；合并后的结果由父任务验证。worker 的完成报告只是一个声明，不能替代整体可运行性。能否强制取消、是否共享文件、后台进程是否仍存活，必须按实际运行时能力处理；不在报告里虚构隔离或已停止。

实现 worker 可在有价值时继承历史，独立审查则应减少实现者结论对输入的影响。还要区分“找代码缺陷”和“验收用户目标”：前者可从 diff 开始，后者必须看到原始目标与被批准的解释，否则可能精确验证了错误目标。fresh context 只是降低一种相关性，不能消除同模型或同规范导致的共同错误。

Cognition 在 2026 年已从早期警告推进到单一写入责任下的审查与咨询；Anthropic 则展示过随着能力提高删除 sprint 分解。这些经验支持按任务测成本和效果，不支持永久固定某一种拓扑或阶段数。[Walden Yan / Cognition, 2026-04-22, field account](https://cognition.com/blog/multi-agents-working)；[Prithvi Rajasekaran / Anthropic, 2026-03-24, harness design](https://www.anthropic.com/engineering/harness-design-long-running-apps)。

## 对八项实践反馈的具体回应

| 反馈 | 改进方向 | 不能用什么替代验收 |
|---|---|---|
| AI 味、黑话、读者负担 | 要求说清主体、条件、动作、影响和下一步；术语面向读者，必要时首次解释；保留真实坏例子和合格改写 | 禁词数、可读性分数或“请自然一点”不能证明读者看懂 |
| 不够目标驱动 | 保存原始目标和确认后的解释；验证完整用户情景；完成报告逐项说明实际结果 | 测试数量、文档齐全、任务全打勾 |
| 中文歧义 | 规范正文可用英文；保留有解释价值的原始中文，用例子明确歧义及被排除含义 | 英文本身不能消除错误解释；双语全文各自维护会增加漂移 |
| 重复犯错、自我进化 | 记录失败机制，选最小改动，验证未见过的同类情况，并保留删除/回退条件 | 每次出错就新增永久规则，或让 agent 自动修改用户目标 |
| 老文档负担 | 当前决定与历史证据分离；局部任务只取必要输入；归档前提炼仍活跃的理由 | 按字节切文件或按时间批量删除 |
| 已确认后一直做到结束 | 内部步骤不自动成为审批点；已经授权的选择连续执行，必要检查由 agent 自己完成 | 在每个阶段说“请确认后我再继续”，或把无回复当成新增授权 |
| 声明与交付不一致 | 双向核对承诺和效果；观察身份、数量、时序、内容与质量条件 | 只从既有测试反推需求全集 |
| 未从用户角度考虑风险与下一步 | 从用户触发到结果解释完整走一遍，包含操作成本、失败、恢复、误解与后续行动 | 页面能显示、接口返回 200、mock 全绿 |

例如，面向插件用户，不应写“映射拓扑异常，进入 reconciliation”。可以写：“发现了 5 个候选脚本，暂时无法确认它们分别对应原来的哪些文件。旧配置已保留；下面列出了候选文件及匹配依据。”这让用户知道现状、影响和下一步，且没有把不确定性伪装成结论。

关于连续交付，应接受用户的核心要求：**已确认并授权的任务内部不要反复设置用户关卡。** 但“中途有新事实就一定是前期没想清楚”太强。运行环境、外部系统和需求解释可能暴露此前无法确认的信息。正确边界是：可调查的自己调查，可逆且仍在授权内的自己解决；只有新发现实质改变承诺、授权、不可逆成本或风险时，才暂停受影响的路径并说明原因。内部证据检查保留，人工签收不随阶段自动增加。

## 自我改进应减少净负担，而不是增加制度库存

建议把真实失败作为输入，但不把每次失败都直接升级成规则。处理顺序是：复原观察和影响；区分信息没到达、解释错误、实现错误、观察遗漏和结束判断错误；选择最便宜且稳定的纠正位置；在相邻但未用于设计的情况上验证；接受、调整或撤回改动。

脚本错误优先修脚本，状态不合法优先在类型或运行边界拒绝，需求误解优先补对照例子，找不到信息优先修读取路径，文字让用户困惑就修实际文案及其写作示例。只在跨场景重复的规则确实需要文字时改 AGENTS。每次还应记录改动替代了什么人工提醒、额外读取或旧规则。

这里尤其需要两道边界。第一，同一个 agent 写的教训和它自己设计的试验容易共同过拟合，应保留未见过的同类任务或独立反馈。第二，能够自动修复局部脚本不代表可以自动修改全局目标、风险预算和验收标准。涉及这些变化仍由人决定；不要让“自我进化”变成自我授权。

评价指标是错误复发、虚假完成、遗漏副作用、人工返工和必要成本；不是 memory 条目数、规则数或新增测试数。模型或运行时升级后，原有脚手架也需要做移除试验，证明删掉后没有丢掉必要结果。

## 模板应如何证明自己有效

保留 checker 的结构职责，另给模板自身增加行为采用评价。这层评价看的是“陌生 agent 学习后怎样做选择”，并不需要一开始开发一个通用评测平台。

从几个可重复的小项目开始：普通 bug；已有实现可复用；测试全绿但用户入口失效；重复请求和错误去重；模糊需求被翻译错；旧 memory 与新授权冲突；压缩后接续；子任务结束但后台仍运行；写给用户的文案难以理解。实际操作、打包产物、受控外部系统和用户结果是主要证据，解释性文字辅助判定。

先准备能够击中已知缺陷的检查：故意断开入口、加入额外效果、重复执行一次、过度去重一次。如果验收抓不到这些有代表性的缺陷，增加 agent 和模板只会扩大不可靠的通过信号。这是对验收灵敏度的局部验证，不是对未知缺陷全集的证明。

随后比较当前模板、缩短入口但保留相关规则的版本，以及针对已发现机制修正的版本。固定代码、任务和可见运行配置；每种情况重复并交错执行。不要同时换模型、运行时和规则后仅凭观感归因。若旧 harness 可运行，可做旧/新 harness × 旧/新纪律的配对比较；若托管服务无法回退，则保留限制，用工具与配置快照支持较弱的归因。

同时看两个层次：规则是否真的送达正确上下文，送达后是否改善行为。把文件加载、模型自称遵循和最终成功混为一谈，会再次误判。效果指标也要分开：目标完成、错误副作用、错误停止/继续、人工纠正，以及时间和 token 成本。危险副作用不能被“更快”抵消。

现有研究提供了有用但冲突的证据。Gloaguen 等的 v1 研究发现人工和生成指令的效果不同，更多测试与探索未必改善任务成功；其范围主要是 Python issue 任务，每条件单次采样。Lulla 等的 v2 摘要则报告效率收益，研究问题与评价方法不同，本次未检查全文，不能拿它做广泛质量结论。[Gloaguen 等, 2026-02-12, §4–5](https://arxiv.org/html/2602.11988v1)；[Lulla 等, 2026-03-30, v2 abstract](https://arxiv.org/abs/2601.20404v2)。

较新的 Khatri 预印本在 17 个任务、3 个仓库、288 个有效评价上，没有测得较大的正确性变化。这并不能证明按需上下文无价值；其任务集小、仍以隐藏测试判断正确性，且对前作范围的概括不够准确。它提醒我们别假定“少读一点一定更好”。这些论文都没有验证本模板在真实长项目中的目标治理。[Prakhar Khatri, 2026-07-28, Methods and Results](https://arxiv.org/html/2607.27250v1)。对“需要本地行为实证”的建议置信度高，对某种上下文布局必然优于另一种的判断置信度低。

## 建议的改动边界与执行顺序

以下是推荐顺序，尚未成为项目优先级，也不是要求用户逐项审批的阶段。

| 现有 owner / 位置 | 建议改变 | 完成证据 |
|---|---|---|
| development、contract/backend/cross-stack 模板 | 把承诺、额外效果、关键数量/时序和用户下一步接到已有验收矩阵；保留原始目标到解释的关系 | 上述四类故障变体及错误对象/部分结果能被发现；不强迫每个小任务填全表 |
| agent-execution、governance、执行计划模板 | 将结果与证据要求保留；明确步骤不自动需要人工签收；不适用的 test-first 方法不制造空测试 | 已授权复杂任务能连续做到可运行结果；新风险出现时只停必要路径 |
| AGENTS、docs map、当前契约 | 精简入口、领域按需路由；提炼活跃决定后移出历史；修新模板继续生成旧代码式标识 | 局部任务减少无关读取，同时不丢授权和验收边界 |
| 原有 handoff/plan | 真实并行或跨会话时补基线、输入、允许效果、产物和回收状态 | fresh/fork、恢复、取消、冲突与集成情景得到观察支持 |
| 实际使用客户端的配置 | 仅配置必要入口桥、可信脚本和可验证 hook | 冷启动、恢复和子任务中有效加载得到验证；未覆盖能力明确记录 |
| 模板自身的测试与 evidence | 保留结构检查，补少量真实采用任务、故障变体和失败回流 | 看见目标改善与人工负担降低，再决定扩大范围 |

应在一次授权变更里形成一个完整的可运行试点：选择代表性任务，落实承诺、实现观察、验证偏差，并完成相关规则与示例的替换。内部按依赖施工即可，不把“已经改好一半文档”当交付节点。通过试点再扩大采用范围，是控制承诺范围；让一个已承诺试点停在半成品，是另一回事。

我不建议当前就做的事情包括：适配全部品牌的插件；统一所有会话格式；创建新的术语体系；把每一项经验升为契约；用 LLM 打一个综合“工程质量分”；或者把现有 checker 扩成需求语义裁判。每一项都可能有场景，但本次证据不足以证明它们的维护成本值得。
